# 2. 마이크로서비스 모델링 방법

```text
상대의 노리를 보면 "세상을 무엇이 떠받치고 있을까?"라는 질문에 "거북이가 떠받치고 있지."라고 대답한 이교도가 떠오른다. 그럼 그 거북이를 떠받치는 것은 대체 뭘까? "그건 또 다른 거북이지."
목사 조셈 프레드릭 버그(Joseph Frederick Berg)
```

마이크로서비스의 첫 걸음은 경계를 찾는데 있다. 
경계를 찾는다는 의미는 도메인 주도 설계와 밀접한 관계가 있는데, 다음 개념을 통해 마이크로서비스 주변의 경계를 그리는 것에 대한 생각의 변화와 다양한 분해 형태(decomposition)를 살펴보자.

- 정보 은닉
- 결합
- 응집력

## 2.1. 뮤직코프 소개

올바른 마이크로서비스 경계를 만드는 기준은 다음과 같다.

본질적으로 마이크로서비스의 독립성에 있다.

- 독립적인 배포
- 독립적인 기능 개발 및 유지보수

본질적으로 독자적인 개발 구현과 배포를 통한 반영이라는 핵심을 생각해볼 때, 염두에 둬야할 문제는 크게 다음과 같다.

정확하게 이해하셨어요 👏
바로 그 부분이 **정보 은닉이 마이크로서비스나 바운디드 컨텍스트 설계에서 핵심적인 이유**입니다.
아래는 그 통찰을 반영해 문장을 자연스럽고 논리적으로 다듬은 버전입니다.

## 2.2.1. 정보 은닉 (Information Hiding)

정보 은닉(information hiding)은 **모듈 경계를 정의하는 가장 효과적인 방법**을 찾기 위해 **데이비드 파나스(David Parnas)**가 제시한 개념이다.

이 개념은 **모듈의 내부 구현 세부사항을 외부로부터 숨기고**, 외부에서는 오직 명확히 정의된 인터페이스를 통해서만 상호작용하도록 하는 설계 원칙을 의미한다. 마이크로서비스 아키텍처에서도 이 원칙은 그대로 적용된다. 서비스가 내부 구현을 철저히 은닉할수록, 시스템은 다음과 같은 특성을 얻게 된다.

- **개발 효율성 향상**
  - 각 서비스가 독립적으로 개발·배포될 수 있어 사이드 이펙트를 최소화한다.
- **도메인 이해도 향상**
  - 서비스가 명확한 도메인 단위로 구분되므로, 해당 도메인 지식의 집중과 이해가 용이하다.
- **유연성 확보**
  - 다른 서비스의 변경 없이 개별 도메인 기능을 자유롭게 확장하거나 수정할 수 있다.

파나스는 다음과 같이 말한다.

```text
모듈 간 연결은 모듈이 서로에게 만드는 가정(assumption)이다. 
- David Parnas
```

여기서 말하는 ‘가정’은 단순한 **통신의 수나 호출 횟수**가 아니라, 한 모듈이 다른 모듈의 **내부 구현이나 동작 방식을 미리 전제하는 지식적 의존 관계**를 의미한다.

따라서 “가정의 수를 줄인다”는 말은, 다른 모듈의 내부 구조나 처리 방식을 알 필요 없이, 공개된 계약(API)만으로도 자신의 기능을 완전히 수행할 수 있게 설계하라는 뜻이다.

가정이 적을수록 모듈 간 결합도는 낮아지고, 한 모듈의 변경이 다른 모듈에 영향을 미칠 가능성도 줄어든다.
결국, 이는 **논리적 독립성**을 확보하는 과정이며, 마이크로서비스의 핵심 개념인 **바운디드 컨텍스트(Bounded Context)와 직결된다.**

각 서비스는 자신의 컨텍스트 내에서 필요한 정보만 알고 동작해야 하며, 다른 컨텍스트의 세부사항에 **침범하거나 의존하지 않는 것**이 중요하다. 이렇게 경계가 잘 정의된 서비스는 내부 변경에도 외부 안정성을 유지할 수 있고, 이는 곧 파나스가 제시한 세 가지 바람직한 특성 **개발 시간 단축**, **이해도 향상**, **유연성 확보** 을 마이크로서비스 환경에서 실현하게 한다.

## 2.2.2. 응집력

응집력(cohesion)은 서로 밀접하게 관련된 기능들이 하나의 단위로 함께 존재하고 함께 변경되는 정도를 의미한다. 즉, **“함께 바뀌고 함께 머무는 코드”**로 정의할 수 있다.

이는 소프트웨어 설계의 핵심 목표 중 하나인, “변경의 이유가 같은 것들은 한곳에 모으고, 다른 이유로 바뀌는 것들은 분리하라”는 원칙을 잘 반영한다.

응집력이 높은 모듈은 다음과 같은 특성을 가진다.

- 기능 확장 용이성 
  - 관련된 로직이 한곳에 모여 있어 기능 개발과 수정이 빠르다. 
- 사이드 이펙트 최소화 
  - 변경 범위가 모듈 내부로 한정되어, 다른 영역에 영향을 주지 않는다. 
- 독립적 배포 가능성 
  - 하나의 목적을 위해 구성된 코드 단위이므로, 별도의 빌드·배포가 용이하다.

이러한 이유로, 마이크로서비스는 도메인(문제 영역)을 기준으로 높은 응집력을 갖는 경계를 찾는 것을 목표로 한다.
즉, 서로 관련된 기능들은 한 서비스 내부에 배치하고,
다른 서비스(경계)와는 가능한 한 느슨하게 연결되도록 설계해야 한다.

반대로, 하나의 도메인과 관련된 로직이 여러 서비스에 흩어져 있다면,
그 시스템은 응집력이 낮다고 할 수 있다. 이 경우, 한 기능을 변경하기 위해 여러 서비스를 동시에 수정해야 하고, 이는 곧 배포 복잡성과 장애 위험으로 이어진다.

결국, 마이크로서비스 아키텍처가 지향하는 것은 “강한 응집력(strong cohesion)”이다. 이는 각 서비스가 하나의 명확한 목적(또는 도메인 책임)을 가지고, 그 목적에 속한 모든 기능이 서비스 내부에 집중되어 있는 상태를 말한다.

정보 은닉이 "경계를 넘어서는 불필요한 의존을 줄이는 것"이라면,
응집력은 "경내 안에서 관련된 책임을 얼마나 잘 모아두었는가"를 의미한다.

## 2.2.3. 결합 (Coupling)

마이크로서비스 아키텍처의 핵심은 **시스템의 다른 부분을 변경하지 않고도 한 서비스를 독립적으로 변경하고 배포할 수 있는 것**이다.

이를 가능하게 하는 핵심 원리가 바로 **느슨한 결합(loose coupling)** 이다.

서비스 간 결합이 느슨하다는 것은, 한 서비스가 다른 서비스의 **내부 구현이나 변경에 거의 영향을 받지 않고** 자신의 기능을 수행할 수 있음을 의미한다. 즉, 서비스 간 관계가 **최소한의 계약(API 수준)**으로만 연결되어 있으며, 상대 서비스의 내부 구조나 처리 방식에 대한 지식이 없어도 동작할 수 있는 상태다.

반대로 **강결합(tight coupling)** 은 다음과 같은 상황에서 발생한다.

- 한 서비스가 다른 서비스의 **내부 데이터 구조나 처리 로직**에 의존할 때
- 통합 방식이 **서비스의 내부 변경을 소비자(호출자)에게도 강제**할 때
- 데이터 또는 이벤트 계약이 **단일 시스템처럼 긴밀하게 연결**되어 있을 때

이런 경우, 한 서비스를 수정하면 다른 서비스도 함께 수정해야 하며, 결국 서비스의 독립적 배포와 변경이 불가능해진다. 이는 마이크로서비스의 가장 중요한 목표 **독립성** 을 훼손한다.

느슨하게 결합된 서비스는 협력하는 다른 서비스들에 대해 **필요한 최소한의 정보만 알고** 동작한다. 이런 특성은 다음과 같은 이유로 중요하다.

- **변경 영향 최소화** : 서비스 간 의존이 줄어들수록, 한쪽 변경이 다른 쪽에 전파되지 않는다.
- **운영 안정성 확보** : 독립적인 배포와 롤백이 가능하다.
- **성능 및 복잡도 관리** : 불필요한 호출이나 데이터 교환이 줄어든다.

특히 서비스 간 **과도한 커뮤니케이션**은 단순히 성능 저하뿐 아니라 **논리적 결합 강화**의 원인이 되므로, 호출 수를 최소화하는 것도 중요한 전략이다.

결합은 단순히 “API 호출의 많고 적음”으로만 정의되지 않는다. 다음과 같은 다양한 형태로 나타날 수 있다.

- **데이터 결합(Data Coupling)** : 동일한 데이터 구조나 스키마를 공유
- **계약 결합(Contract Coupling)** : 변경이 어려운 API 또는 이벤트 계약에 의존
- **시간 결합(Temporal Coupling)** : 서비스 간 요청-응답 타이밍에 의존
- **배포 결합(Deployment Coupling)** : 한 서비스의 배포가 다른 서비스 배포에 종속

이처럼 결합은 여러 수준에서 발생하기 때문에, 서비스 기반 아키텍처에서 **결합을 잘못 이해하거나 과소평가하는 경우**가 자주 발생한다. 따라서 결합은 단순한 통신 구조의 문제가 아니라, **설계 전반에 걸친 구조적 의존 관계의 문제**로 바라보아야 한다.

결국, 마이크로서비스의 이상적인 상태는 “경계 내부는 강한 응집력(strong cohesion), 경계 간에는 느슨한 결합(loose coupling)” 으로 요약된다.

이 균형이 유지될 때, 서비스는 독립성과 유연성을 모두 확보할 수 있다.

## 2.2.4. 결합과 응집력의 연관성(Balance between Cohesion and Coupling)

결합(coupling)과 응집력(cohesion)은 시스템 구조의 품질을 결정짓는 상호 보완적 개념이다. 
두 개념은 서로 반대되는 것이 아니라, **경계 내부와 외부의 관계를 조화롭게 설계하기 위한 균형의 문제**로 이해해야 한다.

논리적으로 연관된 기능이 시스템 전반에 흩어져 있다면, 
이 기능을 변경할 때 여러 경계를 동시에 수정해야 하며, 이는 자연스럽게 **높은 결합도**로 이어진다. 반대로, 관련된 기능이 하나의 경계 안에 모여 있다면 해당 기능의 변경은 경계 내부에 국한되어 **높은 응집력**을 형성하게 된다.

소프트웨어 공학자 **래리 콘스탄틴(Larry Constantine)**은 이를 **콘스탄틴의 법칙(Constantine’s Law)** 으로 정리했다.

> “응집력이 강하고 결합도가 낮은 구조는 안정적이다.”

여기서 말하는 **안정성(stability)** 은 코드 변경 빈도의 문제가 아니라, 
**변경이 시스템 전체로 전파되지 않고 특정 경계 내에 머무를 수 있는 능력**을 뜻한다.

마이크로서비스 관점에서 안정성은 곧 **독립적 배포 가능성(independent deployability)** 로 연결된다. 
서비스 경계가 안정적으로 정의되어 있다면, 팀은 각자의 서비스에서 병렬로 작업하면서도 다른 팀의 변경에 조율하거나 동기화할 필요가 줄어든다.

반면, 한 마이크로서비스가 제공하는 **계약(API 또는 이벤트 스키마)** 이 하위 호환성을 깨뜨리는 방식으로 자주 변경된다면, 
해당 서비스를 사용하는 상위 소비자들도 계속해서 수정해야 한다. 이런 상황은 경계의 안정성이 부족하다는 신호이며, 결합과 응집력의 균형이 깨졌음을 의미한다.

균형의 중요성을 요약하면 다음과 같다.

- **응집력(cohesion)** : 경계 **내부의 통합성**, 즉 관련된 기능이 얼마나 잘 모여 있는가
- **결합(coupling)** : 경계 **사이의 의존성**, 즉 외부와 얼마나 느슨하게 연결되어 있는가

좋은 설계는 두 개념의 **균형(balance)** 위에 서 있다. 
응집력을 높이려다 경계를 과도하게 세분화하면 오히려 결합이 늘어나고, 결합을 줄이려다 경계를 너무 넓히면 응집이 약해진다. 
따라서 시스템의 맥락과 현재의 변화 요구를 고려해 **두 원리 사이에서 최적의 지점을 지속적으로 조정**해야 한다.

세상은 고정되어 있지 않다. 요구사항과 조직 구조가 변하면, 마이크로서비스의 경계 또한 새롭게 정의될 필요가 생긴다. 
즉, **결합과 응집력의 균형은 한 번의 결정이 아니라 지속적인 탐색의 과정**이다.

## 2.3. 결합 유형

시스템에서 일부 결합은 피할 수 없다. 단. 결합 양을 줄이는데 목표를 둬야 한다.

구조적 프로그래밍 맥락에서 결합의 중첩 및 충돌을 평가하는 다양한 모델 중 상당수는 **서비스 기반 상호작용보다는 코드 수준에서 주로 이야기 된다.**

마이크로서비스 아키텍처엔 "도메인", "통과", "공통", "내용" 결합이 존재한다.

```text
도메인 -> 통과 -> 공통 -> 내용
```
_왼쪽부터 느슨한 결합(낮은 수준의 결합) -> 강한 결합(높은 수준의 결합)_ 

각 결합의 형태가 어떻게 발현되는지 살펴보자.

## 2.3.1. 도메인 결합(Domain coupling)

도메인 결합이란 한 마이크로서비스가 다른 마이크로서비스와 상호작용하는 것을 의미한다.
즉, 특정 서비스가 다른 서비스가 제공하는 기능이나 데이터를 필요로 하는 경우 발생한다. 반대로 상호작용하지 않다면 결합도 없다.

마이크로서비스 아키텍처에서 상호작용은 불가피하다. 
일반적으로 도메인 결합은 느슨한 형태의 결합으로 간주된다.

따라서 하나의 마이크로서비스가 너무 많은 책임을 지니면 안 된다. 
예를 들어, 너무 많은 하위 마이크로서비스와 통신해야 한다면 이는 책임이 과도하게 집중된 신호일 있다.

도메인 결합은 데이터 결합과 시간적 결합을 야기할 수 있다.

### 상호작용으로 인한 데이터간의 결합

- 상호작용된 데이터간의 결합은 더 많은 문제를 야기한다.
- 최소한의 상호작용 유지하자
- 데이터 결합에 대한 부분은 "정보 은닉" 개념을 통해 해결 가능하다.
  - 정보 은닉: 필요한 최소한 데이터만 전송하자.
    
### 시간적 결합(temporal coupling)

- 코드 관점에선 순전히 동시에 발생하기 때문에 함께 엮이는 상황을 나타낸다.
- 분산 시스템의 맥락에서는 하나의 마이크로서비스가 작업을 완료하기 위해, 동시간에 어떤 작업을 수행하는 다른 마이크로서비스가 필요한 상황을 나타낸다.
  - 이 의미는 각 서비스는 동작되는 상태여야 하며, 서로 통신(상호작용)할 수 있어야 한다.
  - 예를 들어 `주문`을 하면 `결제`가 된다고 가정하자. 결제 서비스가 동작되지 않는다면 주문 기능 자체가 실패된다. 이를 "시간적 결합"의 형태라 볼 수 있다.
- 시간적 결합은 잠재적으로 리소스 경합과 관련된 문제를 유발할 수 있다.
- trade-off
  - 비동기 메시징, 이벤트 기반 처리 등

## 2.3.2. 통과 결합(pass-through coupling)

통과 결합이란 데이터가 다른 하위 마이크로서비스에 필요하다는 이유만으로 
한 마이크로서비스가 다른 마이크로서비스에 데이터를 전달하는 상황을 의미한다.

- 하위 서비스에서 데이터 구조를 변경하면, 중간 서비스를 거쳐 상위 서비스까지 연쇄적인 변경이 발생한다.
- 클라이언트가 호출 중인 서비스가 내부적으로 다른 서비스를 호출한다는 사실을 알게 되어, 내부 구현이 노출된다.
- 정보 은닉 원칙을 위반하며, 불필요한 데이터 결합을 야기한다.

> "통과 결합"은 구조적 시스템 설계에 대한 실용 지침서(Practical Guide to Structured System Design)에서 설명한 '떠돌이 결합(tramp coupling)'을 의미한다.

통과 결합을 해결하는 핵심 목표는 **변경의 전파를 최소화**하는 것이다.

하위 서비스의 데이터 계약이 중간 서비스를 거쳐 상위 서비스까지 전파되면,
하나의 변경이 여러 서비스를 동시에 수정하도록 강제한다.
이는 마이크로서비스의 독립적 배포 가능성을 훼손한다.

따라서 각 서비스는 다른 서비스의 내부 구현 세부사항을 숨기고(정보 은닉),
자신의 도메인에 필요한 데이터만 주고받도록 설계해야 한다.

통과 결합이 발견되면, 이는 서비스 경계가 잘못 설정되었거나
책임이 적절히 분배되지 않았다는 신호일 수 있으므로, 위 세 가지 해결 방법 중 맥락에 맞는 접근을 선택해야 한다.

### 통과 결합의 해결 방법 1: 중간자 우회 (Direct Access)

- 호출하는 서비스가 중간자를 우회하는 시도가 합당한지 고려하자
- 중간 서비스(B)를 거치지 않고, A 서비스가 C 서비스를 직접 호출하는 방식이다.
  - 기존 A -> B -> C
  - 대안 A -> B, A -> C (병렬 호출)
- 장점:
  - 통과 결합을 제거하여, C의 데이터 구조 변경이 B에 영향을 주지 않는다.
  - A와 C 간의 도메인 결합만 발생하며, 이는 가장 느슨한 형태의 결합이다.
- 단점:
  - 기존 프로세스를 유지하기 위해 A 서비스의 책임이 증가한다.
  - 기존에 B가 담당하던 오케스트레이션 로직(B 처리 완료 후 C 호출)이 A로 이동한다.
  - A가 B와 C 두 서비스 모두에 의존하게 되어, 도메인 결합의 개수가 증가한다.

### 통과 결합의 해결 방법 2: 중간 서비스에서 데이터 생성 및 변환

- A -> B -> C 프로세스는 유지하되, B 서비스가 C에 필요한 데이터를 직접 생성하거나 변환하여 전달하는 방식이다.
- 예를 들어 A가 "사용자 ID"만 전달하면, B가 자체 데이터베이스나 로직을 통해 C에 필요한 "사용자 권한 정보"를 생성하여 C에 전달한다.
- 장점:
  - 통과 결합을 제거하며, 각 서비스가 자신의 도메인에 맞는 데이터만 받는다.
  - A는 C의 요구사항을 알 필요가 없어진다.
- 단점:
  - B 서비스의 책임이 증가한다.
  - B가 C의 요구사항을 알아야 하므로, B와 C 간 결합이 강해질 수 있다.

B가 C에 필요한 데이터를 이미 가지고 있거나, 쉽게 생성할 수 있을 때 적합하다.

### 통과 결합의 해결 방법 3: 중간 서비스의 데이터 무관심 (Pass-through with Opacity)

- A 서비스가 C를 위해 보낸 데이터를 B는 불투명한 데이터 덩어리(opaque data)로 취급한다.
- B는 해당 데이터의 내부 구조를 파싱하거나 해석하지 않고, 단순히 C로 전달만 한다.
- A 에서 보낸 C 를 위한 데이터를 B 에선 그냥 전달만 한다면, B 서비스는 독립적인 경계를 지킬 수 있다.

- 구현 방법:
  - 제네릭 타입 사용 (예: Map<String, Object>, JSON 문자열)
  - 별도의 메타데이터 영역에 포함 (예: HTTP 헤더, 이벤트의 context 필드)
- 장점:
  - C의 데이터 구조 변경이 B에 전파되지 않아, 변경 영향을 차단한다.
  - B 서비스가 자신의 경계를 유지할 수 있다.
- 단점:
  - A와 C 간의 암묵적 결합이 여전히 존재한다.
  - B는 자신이 전달하는 데이터의 의미를 모르게 되어, 디버깅이나 모니터링이 어려워질 수 있다.
  - 데이터 검증이나 보안 처리가 어렵다."

## 2.3.3. 공통 결합(common coupling)

공통된 데이터를 여러 서비스에서 사용하는 경우에 발생한다.

예를 들어:
- 공유 데이터 베이스 사용
- 공유 메모리나 공유 파일 시스템 사용

### 공통 결합 문제점

공통 결합의 주된 문제점은 공통된 값 변경시 각 서비스에 전반적인 영향을 미친다는 점이다.

- 변경 영향의 전파
  - 공통 데이터 변경 시 모든 서비스에 영향
  - 스키마 또는 API 버전 하위 호환
    - 공통 데이터를 여러 서비스가 수정 가능한 경우, A → B → C 같은 호출 체인에서 A가 스키마를 변경하면 B, C에 즉각 영향을 미친다. 
    - 이때 하위 서비스가 호환되지 않는 변경을 거부할 수 있는지 확인해야 한다.
  - 독립적 배포 불가능
- 리소스 경합
  - 공통 파일 시스템이나 데이터베이스를 사용할 경우 해당 공유 리소스에 과부하가 걸릴 수 있다.
  - 공유 자원이 느려지거나 아예 사용할 수 없게 될 경우, 장애 전파의 위험성이 크다.
  - 여러 소비자가 공유 데이터베이스에 임의의 쿼리를 실행할 수 있고 결국 매우 다양한 성능 특성이 발생할 수 있기 때문이다.

### 공통 결합의 완화 방법

불가피하게 공통 데이터를 사용한다면, 읽기 전용으로 설정하는 편이 비교적 좋다.

단. 데이터 구조가 자주 변경되거나 여러 마이크로서비스가 동일한 데이터를 쓰고 있는 경우 공통 결합은 문제가 된다.

이런 경우엔 하나의 마이크로서비스가 상태의 관리를 책임지도록 구성한다.

## 2.3.4. 내용 결합(Content coupling)

상위 서비스가 하위 서비스의 내부까지 도달해 서비스의 내부 상태를 직접 변경하는 상황을 뜻한다.

**대표적인 예시:**
- 현재: - 다른 서비스의 데이터베이스에 직접 접근하여 데이터를 변경
- 제안: - 주문 서비스가 재고 서비스의 데이터베이스에 직접 접근하여 데이터를 변경

### 공통 결합과의 차이

내용 결합과 공통 결합은 미묘한 차이가 있다.

**공통점:**
- 두 경우 모두 공통 데이터 집합을 읽고 쓴다.

**차이점:**
- **공통 결합**: 공유된 외부 의존성(예: 외부 인사 시스템 DB)을 여러 서비스가 사용한다.
  이 의존성은 우리의 통제하에 있지 않다.
- **내용 결합**: 특정 서비스가 소유한 내부 리소스를 다른 서비스가 직접 침범한다.
  소유권 경계선이 명확하지 않아 개발자가 시스템을 변경하기 어렵다.

### 내용 결합의 특수한 문제 (병적인 결합)

공통 결합에서 발생하는 문제가 내용 결합에서도 발생하는 것은 분명하지만,
내용 결합에는 일부 사람들이 **병적인 결합(pathological coupling)** 으로 부르기에 충분한 추가적인 문제가 있다.

마이크로서비스에서 작업할 때는 **자유롭게 변경 가능한 부분**과 **그렇지 못한 부분**을 명확하게 분리하는 것이 중요하다.

- 개발자는 서비스가 외부에 노출하는 **계약(API)** 부분의 기능 변경 시점을 신중히 결정해야 한다.
- 반면, 마이크로서비스가 노출하는 계약에 영향을 주지 않는 **내부 구현**은 자유롭게 변경할 수 있다.

**내용 결합의 핵심 문제:**

외부 서비스가 여러분의 데이터베이스에 직접 접근하도록 허용하면,
데이터베이스 스키마가 실제로 **외부 계약의 일부**가 되어버린다.

원래 DB 스키마는 내부 구현으로서 자유롭게 변경 가능해야 하지만,
다른 서비스가 직접 접근하는 순간 변경이 불가능한 외부 계약이 된다.

결과적으로 **변경 가능한 부분과 변경 불가능한 부분을 쉽게 추론할 수 없게** 된다.
이는 **정보 은닉 개념이 완전히 사라진 셈**이다.

**예시:**
재고 서비스의 inventory 테이블:
- 원래는 재고 서비스만 사용 (내부 구현 → 자유롭게 변경 가능)
- 주문 서비스가 직접 접근 시작
- 이제 테이블 구조가 "외부 계약"이 됨 (변경 불가능)
- 컬럼명 변경, 정규화 등 내부 개선이 불가능해짐

### 해결 방법

다른 서비스의 데이터베이스에 직접 접근하지 말고,
반드시 해당 서비스가 제공하는 **API를 통해서만** 데이터를 변경해야 한다.

이렇게 하면:
- API = 외부 계약 (신중히 변경)
- DB 스키마 = 내부 구현 (자유롭게 변경)

## 2.4. 딱 도메인 주도 설계만큼

마이크로서비스 경계를 정의할 때 기본 메커니즘은 도메인 모델을 생성하기 위해 도메인 주도 설계(DDD)를 사용하며 도메인 자체를 중심으로 진행한다.

> 경계란 변경될 수 있는 부분과 변경 불가능한 부분을 의미한다.

- 보편 언어
  - 의사 소통을 돕기 위해 코드와 도메인 설명에 사용할 공통 언어를 정의하고 채택한다.
- 애그리거트
  - 객체들의 집합이며 일반적으로 실제 세계 개념과 관련된 하나의 개체로 관리된다.
- 경계 콘텍스트
  - 더 큰 범위의 시스템에 대한 기능을 제공하지만 복잡성을 숨기는 비즈니스 도메인 내부의 명시적인 경계다.

### 2.4.1. 보편 언어(Ubiquitous language)

보편 언어란 실제 사용자가 사용하는 언어를 프로그램 코드에서도 동일하게 사용하도록 노력해야 한다는 개념이다.

프로그램을 넘어 실제 타 부서와의 커뮤니케이션 또는 같은 프로젝트의 일원들이 커뮤니케이션에서 사용하는 언어(단어)를 의미한다. 
이를 통해 원할한 커뮤니케이션을 통한 도메인 지식을 공유하며 발전할 수 있고 공통 목표를 함께 나아갈 수 있다.

보편 언어와 코드 간 불일치는 번역 과정에서 오역과 불필요한 커뮤니케이션을 야기한다.
따라서 처음부터 보편 언어를 명시하고 이를 코드에 반영하는 것이 중요하다.

### 2.4.2. 애그리거트(Aggregate)

DDD에서 애그리거트(aggregate)는 다소 혼동되는 개념이자 다양한 정의가 존재한다.

### 애그리거트와 마이크로서비스의 관계

하나의 마이크로서비스는 하나 이상의 애그리거트를 관리할 수 있다.

애그리거트는 일반적으로 수명주기(lifecycle)가 있으며, 
하나의 마이크로서비스에선 여러 애그리거트가 존재하지만, 하나의 애그리거트는 여러 마이크로서비스에 관리되면 안된다.

다른 서비스의 기능이 애그리거트 변경하려는 경우:
- 해당 애그리거트에 직접 변경 요청을 하거나
- 애그리거트 스스로 시스템의 다른 구성 요소와 상호작용해서 상태 전환이 이뤄져야 한다.
  - 예를 들어 다른 서비스에서 발행한 이벤트를 구독하여 처리할 수 있다.

무엇보다 상태 전이를 애그리거트가 거절할 수 있다는 점도 명심하자.

애그리거트는 다른 애그리거트와 관련성을 가질 수 있다.
- 하나의 `고객` 애그리거트는 하나 이상의 `주문`이나 `관심 목록` 애그리거트와 연관될 수 있다.

### 애그리거트 간 관계 모델링

같은 마이크로서비스에 여러 애그리거트의 관계는 데이터베이스의 외래키 설정으로 표현하여 모델링할 수 있다.

하지만, 다른 서비스에 있는 애그리거트와의 관계는 다르게 모델링해야 한다.

- 방법 1: 외부 애그리거트의 ID를 관리하는 방법:
  - 외부 애그리거트의 ID만 관리하고 외래키를 설정하지 않는 방법
  - 장점: 외래키를 사용하지 않아 테이블 간 결합을 느슨하게 유지
  - 단점:
    - 관계의 의미가 명확하지 않다. 
    - 해당 ID가 실제로 어떻게 사용되는지는 외부 서비스의 코드를 확인해야만 알 수 있다.
- 방법 2: 외부 REST 기반 시스템의 URL 관리
  - 명확한 관계가 이뤄지도록 고객의 ID 대신 URL를 저장 관리한다.
  - 장점:
    - 관계의 특성이 명시적이다
    - URL를 직접 역참조해 직접 외부 자원을 조회할 수 있다.
      - 모조 URL 스킴(pseudo-URL scheme)을 활용하면 REST가 아닌 시스템에서도 URL 방식의 명확성을 활용할 수 있다.
      - 예: `soundcloud:tracks:123`은 SoundCloud 서비스의 ID가 123인 트랙 참조
      - 프로토콜 부분(`soundcloud:`)으로 어느 서비스인지 명확히 알 수 있음
  - 단점:
    - URL api 변경시 디비 컬럼의 마이그레이션이 필요할 수 있다.
    - 언제든 변경 가능성이 있으므로 일회성 추적 조회라고 볼 수 있다.

### 애그리거트 설계 원칙

시스템을 애그리거트로 분해하는 방법은 여러 가지가 있으며, 일부 선택은 주관적일 수 있다.
초기 설계 시에는 **시스템 사용자의 멘탈 모델(mental model)** 을 우선적인 지침으로 삼는 것이 좋다. 
이후 성능 문제나 구현의 복잡성이 발견되면, 애그리거트 경계를 재구성할 수 있다.

> 멘탈 모델이란 개발자와 도메인 전문가(비즈니스 담당자)가 비즈니스 도메인(문제 영역)에 대해 공유하고 이해하는 개념적 모델, 
> 즉 마음속의 그림을 의미하며, 이 멘탈 모델을 소프트웨어 코드에 일치시켜 '모델 주도 설계'를 통해 도메인 개념을 코드에 명확히 반영하고 유비쿼터스 언어로 소통하는 것이 DDD의 핵심 목표입니다. 
> 즉, 도메인 전문가의 머릿속 세계와 개발자의 코드 세계 사이의 '표현적 차이(Expression Gap)'를 최소화하는 것이 중요합니다.
